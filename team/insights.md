## Error analysis (where the models fail) and what we tried
- #29 (local diagnostic on commit cc84694, not a lab run): the interim M4 calls a 50 % string outage a **sensor fault** on 5 of 8 clean battery sites of the hero feeder and gets it right on all 7 no-battery sites: battery charge/discharge in the residual looks like a logger problem to a model trained on #14's synthetic data. Tried: nothing in the model yet; the demo pins a battery site M4 reads correctly (S0284 -> 1042) and says so. Fix belongs to the fleet retrain (#14).
- #29 replay#380 (interim weights): the same site flips from string_outage (day 3) to sensor_fault (day 4) as the 24 h window fills with outage-only data -> excluded instead of derated: M4 has seen few windows that start inside a long outage.
- #29 replay#380 / #506: #41's curtailment veto (≥ 15 % of the park at one power ceiling) misses a cap to 0 % — near-zero noisy power has no common ceiling — so a 70-turbine park-wide cap was classed normal although the classifier's p(non-normal) was ≈ 0.999. Tried: a replay-side park consensus on M6's own curtailment probabilities (≥ 50 % of the park above threshold): the cap becomes one curtailment alert (105.5 MWh, no work order). Proper fix: add the consensus feature to #41's decide().
- #29 replay#380 (interim weights): M4 sends 5 sites (15 rows) to human review on OOD (robust-z ≥ 3) — sites whose recorded metadata or profile is outside #14's synthetic training range; unseen-site behaviour needs the fleet retrain.
- #14 / #67 run#228: models trained on #14's own generator transfer poorly to the shared fleet (load coverage 0.44, PV behind LightGBM): the domain gap between two synthetic generators is already large, so real-data claims need real data (PVDAQ run failed).
